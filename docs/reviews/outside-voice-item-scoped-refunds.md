**1. Novelty vs. "cap in disguise"**
Genuinely different, not just a relabeled cap. A cap validates a number the agent chose; this removes "amount" from the tool's input schema entirely, so the agent's only degrees of freedom are which of a small, enumerable, trusted set of item IDs to name. That's least-authority interface design (same category as parameterized SQL vs. string-built SQL), not a bound on the same channel. But it isn't a replacement for caps+approval — the design still needs the cap (total > cap escalates) and the approval path (full-order refund escalates) as backstops. So: novel at the interface layer, dependent on the existing caps/approval machinery to catch the edge cases item-scoping doesn't resolve by itself.

**2. Top 5 breaks + cheapest mitigation**

- **Order data poisoning**: if "trusted" order data is fetched via a path the agent can influence (agent-supplied order_id, or a lookup not bound to the capture being refunded), the trust anchor is fake. *Fix*: fetch order data server-side keyed off capture_id only, never accept order_id/order data from agent context; verify order↔capture binding before computing amount.
- **Item ID confusion**: duplicate/similar SKUs, bundles, or near-identical item descriptions let the agent select a pricier item than the ticket justifies. *Fix*: validate item_ids strictly against the enumerated line-item set for that order; log item description + price in the audit entry so a human reviewer can eyeball mismatch between ticket text and selected item.
- **Partial quantities**: a line item with qty 3 can't be partially refunded without reintroducing an agent-chosen number (qty × price = amount). *Fix*: let the agent pick qty from the bounded range [1, line_qty], gate computes amount, and escalate whenever requested qty == full line qty (apply the same "all = escalate" rule per-line, not just per-order).
- **Shipping/tax/discount lines**: not real "items," so either unrepresentable (under-refund complaints) or, if modeled as pseudo-items, a backdoor to inflate amount under a non-merchandise label. *Fix*: exclude tax/shipping/discount from the agent-selectable item set entirely; compute any proportional shipping/tax adjustment server-side from the merchandise items selected, never agent-specified.
- **Multi-ticket/session structuring**: several refund_items calls, each under the per-order cap/full-order threshold, cumulatively drain the order or exceed a cap if checks are scoped per-call instead of per-order lifetime. *Fix*: check "total refunded so far" and "items refunded so far" against the order/capture in the existing atomic SQLite ledger, not just the delta in the current call.

**3. Score with this feature: 7/10.** It's a real mechanism-level insight with a before/after number, not just another guardrail — that's rare in a hackathon demo. Not 8-9 because the underlying pattern (narrow the interface instead of validating the output) is a known security technique newly applied here, and the evidence (n=20, one model, builder-authored tickets) is thin enough that it demonstrates the idea without proving it holds under adversarial pressure.
**Highest-leverage single addition**: bind order-data retrieval to capture_id server-side (kill order_id as an agent-supplied value). Without that, the first attack above collapses the whole item-scoping guarantee back into "agent-controlled amount, one hop removed" — it's the one gap that, left open, negates everything else on this list.

**4. Overclaim risk**: stating or implying "item-scoped refunds eliminate agent over-refunding" / "the agent cannot cause an over-refund." False — the agent can still select every item and get the full order amount; what actually prevents the over-refund is the escalation-to-human path, not the item-scoping itself. The honest claim is "amount-manipulation is converted into a finite, auditable item-selection problem that the existing escalation logic catches" — not "solved." The 0-of-20 figure shouldn't be presented without the n=20/one-model/author-written-tickets caveat already listed in the honest limits.

Recommendation: ship item-scoped refunds as the headline feature and add the capture_id-bound order-data fetch before demo, because that single fix removes the one attack that would fully undercut the novel claim on stage, and the rest of the gaps (quantity, tax lines, structuring) are defensible as "known limits, same backstop (caps+approval) already catches them."
